01 · PROBLEM

Navigation alone was not enough.

The project began as an indoor campus-navigation idea. After faculty feedback, the scope expanded into a broader operations layer where room allocation, class schedules, faculty changes, student notifications and navigation can respond to one another.

Core system question

What should happen when a room or class changes after the timetable has already been created?

05 · TESTING

The useful test was not whether a route line appeared.

I moved toward a more structured synthetic campus dataset so expected room relationships, occupancy and routes could be checked rather than merely demonstrated. The process exposed that the spatial model still needs stronger architectural detail and clearer room, door and path relationships before navigation quality can be meaningfully judged.

Workflow verified

The faculty room-change flow can propagate through the system to affected student-facing information.

What the test changed

I stopped treating a visible route as evidence that the indoor-navigation model itself was accurate.

Remaining application issues

Student sign-up/login, contact-email connection and role-specific forgot-password flows remain areas to finish or harden.

Navigation limitation

Validation still depends on a more detailed spatial dataset representing geometry, doors, corridors, stairs and relationships between spaces.

07 · VALIDATION BOUNDARY

A working prototype can prove system flow without proving deployment readiness.

Controlled synthetic data can test whether application logic behaves as expected. Real positioning accuracy, architectural-grade mapping, production authentication, reliability under load and deployment on an actual campus remain separate validation steps.

Current description

Working academic prototype — not a claim of production deployment or validated indoor-navigation accuracy.
